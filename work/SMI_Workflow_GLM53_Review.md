# 二、重点问题展开

## Q1：预算与并行是否自洽、最优？600s 怎么分最稳？

**数值上自洽，策略上非最优。**

- 自洽性：单 agent 180s + 冷启动/调度 60–90s ≈ 270s ≪ 600s，并行 2–3 个（文件不相交）不改变 max，安全。
- 非最优之处：预算应按**最坏情况+余量**设计，不是"填满上限"。风险严重不对称——多拆一批 workflow 只花 ~1 回合，超时一次赔 10 分钟+产物核对混乱。**宁可 3 批各 200s，不要 1 批 550s。**
- 推荐分配表：
  - workflow 计划总墙钟 ≤ **450s**（75% 上限，留 150s 兜底）；
  - 单 agent 设计墙钟 ≤ **180s**，通过"≤4 项精准改动 + 命令白名单"实现（时间本身不可执行）；
  - 并行度 = min(互不相交文件组数, 3)；
  - "两个大文件十几项改动"的正确拆法：**按文件边界分组**（不是按项数机械拆），同文件多项归一个 agent；超预算则分批 workflow 或主控直做。

## Q2：主控直做 vs 派 agent 的判据？

现有分界可用，升级为三条硬判据：

1. **锚点判据**：主控已持有文件路径+唯一字符串锚点、无需探索性读取 → 主控直做（同回合并行发多个 edit）。
2. **成本判据**：若写任务书需主控先花 ≥2 回合读文件，而主控 1–2 回合能改完 → 直做。派 agent 的前提是任务书写作成本 < 直做成本——因此任务书应**目标导向+验收样例**，探索定位下放给 agent，不要替 agent 把路探完。
3. **体量判据**：>~100 行新代码/新文件、跨多文件同模式重复 → flash agent；探索型改动（先找位置）→ agent（省主控回合+上下文）。

## Q3：验证并发化的防扩散？

四层防控：

1. **两级门禁**：L0 = py_compile / import / `git diff --stat` 改动范围核对（秒级，**串行**，派发下游、提交前必过）；L1 = 受影响文件的选择性 pytest / 基线（后台）。不可把 L0 也后台化——它是防扩散的紧门禁。
2. **依赖链规则**：B 依赖 A 的产物时，必须 A 的 L0 通过 + diff 范围与任务书一致才可派 B；若必须并发，B 只能改与 A 不相交的文件。
3. **隔离**：L1 在 `git worktree`/目录副本上跑，与后续编辑互不污染；以**脱离进程**方式启动（`Start-Process` 重定向到日志文件，尾部追加 DONE 标记），主控轮询日志文件而非持有 job 对象；带超时 kill 防僵尸 pytest。
4. **Gate 收割**：提交前、送审前、派发依赖型下游前、任务切换前，强制收割全部 L1 结果，未收割不得过 gate。

## Q4：ChatGPT 轮询与停滞窗口？

- 协议保留：matched + generating=false + 指纹两次一致 → 取全文，且确认与取回**连续执行**，其中第二次指纹间隔压缩到 30–60s。
- 节奏改为**首探提前+退避**：发送后 90s → 180s → 300s → 之后每 300s。判据是状态谓词，与探测间隔无关，粗化间隔不增加误判，只推迟"发现完成"的时刻——首探提前正好补偿。
- 停滞窗口的保留方式：若 600s 窗口是**硬性评审要求** → 保留窗口本身，但窗口内全部塞填隙任务（派 agent、跑 L1、写下一份任务书草稿），纯等待成本压到零；若窗口是自家为防中间态设计的 → 等效替换为"谓词 + 两次指纹间隔 ≥60s"。
- 补充：若指纹连续两个周期不变但 generating=true，判定疑似卡死，走重发/人工决策，不无限等。
- 硬规则：**发送后当回合确认"已发出"即返回；任何等待不得置于 workflow 内**——历史那次 600s 阻塞就是这么来的。

## Q5：单分支 vs 两提交溯源？

不冲突，且更优。输入 commit 与报告 commit 同链可 diff。三个纪律：送审即钉哈希；评审期间禁 history 改写；报告以新 commit 顺序追加。仅当评审方只接受分支名时，加一个 fast-forward-only 指针分支（零 cherry-pick）。

## Q6：批量调用 vs 多 agent 并行？

无内在冲突，条件有三：仅独立调用同回合并行；workflow 独占回合；同文件多 edit 用字符串锚点。另推荐**"发射台回合"模式**：进入任何 workflow 前的那个回合，把所有可并行事项（L1 后台启动、review 发送、下一批 read 预取）一次性全部发出，阻塞期间后台一切照转。

## Q7：遗漏的更大头浪费（按预期收益排序）

1. **无超时恢复协议**：超时后盲目整单重跑，每次再赔 10 分钟——这是当前最大的单项损失源。须改为"报错后先读 done 清单 + diff --stat 核对产物，只补发缺失项"。
2. **长等待置于 workflow/前台**（历史 600s 阻塞实例）——须彻底移出。
3. **全量验证跑在关键路径**——应选择性（受影响文件）+ 后台。
4. **步骤导向任务书**迫使主控先探索再派发——改目标导向，回合数直降。
5. **主控上下文膨胀**（整读大文件核对产物）——改 diff --stat/清单式核对。
6. **pwsh job 跨回合死亡**导致验证静默丢失后重跑——脱离进程+日志。
7. **同文件多 agent 冲突返工**——文件边界分组。
8. **周期末忘收割后台结果**——强制收割清单。
9. git 杂操作分散多回合（小头）——合并进发射台回合。

# 三、Q8 最终执行规程

1. **任务书白名单制**：agent 仅允许 edit/read/py_compile/git status，禁一切测试套件、基线、网络、pip、循环探测；≤4 项精准改动、按文件边界分组；任务书写目标+验收样例，不写探索步骤。
2. **预算**：单 agent 设计墙钟 ≤180s，workflow 计划总墙钟 ≤450s（含 60–90s 冷启动余量），超出必拆多批，宁小勿大。
3. **并行规则**：单 workflow ≤3 个 agent，改动文件集（含临时/日志输出路径）两两不相交；同文件多改动归一个 agent 或主控直做。
4. **超时恢复**：每个 workflow 的最后动作是让 agent 写 done 清单（文件+改动摘要）；workflow 报错后先读清单+diff --stat 核对，只补发缺失项，禁止整单重跑。
5. **主控直做判据**：已持有唯一字符串锚点且 ≤3 处局部 edit → 主控同回合并行 edit；探索型、>100 行新生成、跨文件同模式重复 → flash agent。
6. **两级验证**：L0 = py_compile+import+diff --stat 范围核对（秒级、串行、过 gate 必经）；L1 = 受影响文件的选择性 pytest/基线（后台）。
7. **后台验证机制**：脱离进程启动、输出重定向日志文件、尾部 DONE 标记、带超时 kill，在 git worktree/目录副本上执行；主控轮询日志文件，不依赖会话内 job 对象。
8. **Gate 收割**：提交前、送审前、派发依赖型下游前、任务切换前，必须收割全部 L1 结果并确认通过，否则停下。
9. **ChatGPT 轮询**：发送当回合确认已发出即返回，等待绝不入 workflow；探测节奏 90s→180s→300s→每 300s；出现 matched+generating=false 后 30–60s 内二次指纹，一致立即取全文；硬性 600s 窗口则保留但塞满填隙任务。
10. **卡死检测**：指纹连续两周期不变且 generating=true → 判异常，重发或升级人工，不无限等。
11. **Git 纪律**：单分支顺序 commit，送审钉输入哈希、报告用新哈希，期间禁 rebase/amend；评审只收分支名时加 fast-forward-only 指针分支。
12. **回合纪律**：独立短调用（read/probe/后台启动）同回合并行；进入 workflow 前打"发射台回合"把所有可并行事项一次发出；同文件多 edit 用唯一字符串锚定。
13. **周期末收割清单**：后台验证日志、ChatGPT 探测状态、未验证产物、未提交改动——逐项清零后才进入下一周期。
14. **上下文卫生**：产物核对一律用 diff --stat/清单/文件头尾，不整读大文件，旧日志只留摘要。

一句话结论：你的 v2 已抓住主因（任务书瘦身、并行、分层、交错轮询），把它从"方向正确"推到"可执行正确"缺的是四块水泥——**内容化预算、超时恢复、两级门禁+gate 收割、后台进程存活性**——补上即为终版。
