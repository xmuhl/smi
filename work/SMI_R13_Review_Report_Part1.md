# 3. R12 tracks 动态化方案复核

## 3.1 可保留的设计

### A. “种子赛道 + 动态候选”双层结构是合理的

相比完全静态清单，动态池能反映短期市场主线；保留 4 条种子赛道又能避免完全被短期资金波动主导。方向上比“全静态”或“全动态”都更稳健。

### B. 5 日成交额排名用于刻画流动性/关注度是合理的

5 日窗口能够弱化单日异常成交，相比只使用当日成交额更适合作为“主赛道候选”的第一层筛选。

### C. 当日净流入 > 0 用作方向过滤具有业务解释性

它能够避免仅因成交活跃、但资金方向明显为负的板块直接进入动态池。

### D. 双底座归档是正确方向

动态选池和评分历史天然存在时间依赖。将行业 universe 与历史快照归档下来，是后续实现可复算、可验收、可回放的必要基础。

### E. 四维评分优于单指标排名

`25/35/25/15` 至少从设计上避免了单一成交额、涨幅或资金流指标一票决定结果。权重本身是否合理，要等第2步核对四个维度的实际定义、归一化、缺失值和分母口径。

# 4. 新问题清单

## R13-P2-01 — 动态候选准入缺少稳定性与历史就绪约束

**严重度：** P2  
**状态：** `NOT_CLOSED`  
**定位：** R12 tracks 动态选池设计（送审说明层面）  
**证据：**
- 动态候选规则为“近 5 日成交额排名 ≤8 且**当日**净流入 >0”；
- 动态候选 close 历史“自入选次日起累积”；
- `excessReturn20d` 等维度又依赖历史；
- 当前 coverage 常态只有约 71%~82%。

### 根因

当前选池规则把“今天是否应成为候选”和“今天是否具备完整评分数据”视为近似同一件事，但它们实际上是两个状态：

1. **市场资格状态**：今天是否足够活跃、资金是否流入；
2. **数据就绪状态**：是否已有足够历史数据支撑 20 日等评分维度。

新入选板块天然可能满足前者、却不满足后者。

同时，“当日净流入 >0”是一个单日门槛；排名 `8/9` 之间也是硬切线。若没有迟滞或连续确认机制，动态池容易因为一天的资金翻正/翻负或排名轻微变化而反复进出。

### 影响

- 候选池 churn 增大；
- 新候选反复引入历史冷启动；
- coverage 下降不是“采集失败”，而是**选池制度主动制造的数据不成熟**；
- 与硬 coverage=80 叠加后，可能频繁把整个 tracks 模块打为 `UNAVAILABLE`；
- 页面用户看到“获取失败”时，会把设计性缺失误解成基础设施或采集器故障。

### 建议

将“发现池”“预热池”“正式评分池”拆成三个逻辑层：

1. **发现池**：仍可使用 5 日成交额排名 + 当日净流入；
2. **预热池**：对更宽的候选集合持续归档历史，而不是等正式入选后才开始累积；
3. **正式评分池**：满足市场资格 + 最低历史就绪条件后才进入可评分集合。

同时增加迟滞：
- 入池：建议至少 2 个交易日满足条件，或 3 日中满足 2 日；
- 出池：建议连续 2 日不满足再退出；
- 排名可使用“进入阈值 ≤8、退出阈值 >10/12”的双阈值，而非 8/9 单点翻转。

> 注意：具体阈值需要用真实历史样本回放校准；Part 1 不把上述数字冒充已验证最佳值。

### [FIX:R13-P2-01] 设计级可应用修订

> **本块是设计契约，不冒充现有 `config/tracks.yaml` 的真实字段名。第2步读取源码后，应把该契约映射为项目现有配置项和完整函数。**

将 tracks 动态候选规则改为以下完整契约：

```text
TRACKS_DYNAMIC_POOL_POLICY_V4

1. 发现池（discovery pool）
   - 保留近 5 个交易日成交额排名筛选；
   - 保留资金净流入方向筛选；
   - 发现池只代表“值得跟踪”，不等于“立即进入正式评分”。

2. 预热池（prewarm pool）
   - 对发现池及其邻近排名集合持续归档评分所需历史；
   - 不允许“首次正式入选后才开始历史积累”成为默认路径；
   - 预热数据不得直接提升评分，只用于消除后续冷启动。

3. 正式评分池（scoring pool）
   - 必须同时满足：
     a) 市场资格；
     b) 关键身份映射成功；
     c) 最低历史就绪条件。
   - 不满足历史条件的候选标记为 WARMING_UP，不计为采集失败。

4. 迟滞
   - 入池必须经过连续确认或窗口确认；
   - 出池必须经过连续失配确认；
   - 排名进入阈值与退出阈值分离，避免 8/9 附近抖动。

5. 状态语义
   - WARMING_UP 与 FETCH_FAILED 必须分开；
   - 设计性历史不足不得直接呈现为“获取失败”。
```

## R13-P2-02 — coverage=80 单硬门槛过于激进

**严重度：** P2  
**状态：** `NOT_CLOSED`  
**定位：** tracks coverage fail-fast 策略  
**证据：**
- 常态约 `82.4%`；
- hard threshold=`80%`；
- 正常余量只有 `2.4pp`；
- 2026-08-20 已跌至 `71.4%` 并直接 `UNAVAILABLE`；
- 另有 `HS300_SEED_UNAVAILABLE` 这一明确、长期存在的历史源缺口。

### 根因

一个 hard threshold 同时承担了三种不同含义：

1. 数据质量是否完整；
2. 评分置信度是否足够；
3. 整个模块是否还能提供有用信息。

这三者不应被压缩成一个布尔门。

在“结构上存在不可恢复缺口”的情况下，把常态 coverage 的安全边界设在只有 2.4pp 的位置，相当于让正常数据波动直接触发模块级不可用。

### 影响

- 一项或少数维度缺失可以把整个模块从“部分可用”打成“不可用”；
- 用户界面发生“时好时坏”的状态抖动；
- 可用的其他三维评分和种子赛道信息被全部丢弃；
- 监控告警难以区分“关键数据断供”和“可降级缺失”。

### 判断

**是，80 的 fail-fast 设计过激。**

问题不只是“80 应不应该改成 75”，而是应从**单阈值二态**改成**关键字段门禁 + coverage 分级**。

### 推荐模型

建议最少拆成三态：

- `AVAILABLE / FINAL`：coverage 达到稳定目标，关键维度齐全；
- `PARTIAL / DEGRADED`：coverage 下降，但仍有足够信息可评分；
- `UNAVAILABLE`：关键身份/核心输入缺失，或者 coverage 低到无法形成可信输出。

不要让非关键维度缺失直接触发模块级 `UNAVAILABLE`。

### 阈值建议

在未完成历史统计前，不建议把某个新数字直接固化成最终规则。可采用：

- **目标线：80%** —— 保留为“完整度目标”，而不是硬失败线；
- **临时 hard floor：约 65%~70%** —— 只作为过渡值；
- 用至少 20~30 个交易日的真实 coverage 分布重新标定 hard floor；
- 最终 hard floor 建议基于正常分布的 P5/P10、一个字段等效损失幅度和关键维度权重共同决定。

当前 `71.4%` 更适合进入 `PARTIAL/DEGRADED`，除非缺失的是被定义为不可替代的关键输入。

### [FIX:R13-P2-02] 设计级可应用修订

```text
TRACKS_COVERAGE_GATE_V2

1. coverageTargetPct = 80
   - 语义：质量目标，不是模块死亡线。

2. coverageHardFloorPct
   - 在历史样本校准完成前使用临时值 65~70；
   - 上线最终值前，必须用至少 20~30 个交易日 coverage 分布回放验证。

3. 状态判定
   A. 若关键输入缺失：
      -> UNAVAILABLE
   B. 若 coverage < hard floor：
      -> UNAVAILABLE
   C. 若 hard floor <= coverage < target：
      -> PARTIAL/DEGRADED
   D. 若 coverage >= target：
      -> AVAILABLE/FINAL

4. 关键输入单独定义
   - 身份映射失败；
   - 无法形成任何核心评分；
   - 关键价格/日期身份不一致；
   上述才允许绕过 coverage 直接 fail-closed。

5. 非关键维度缺失
   - 降低置信度和 coverage；
   - 保留其余可用评分；
   - 不得自动压成整个 tracks=UNAVAILABLE。

6. 输出必须至少区分：
   - coveragePct
   - missingDimensions
   - criticalMissing
   - decisionReason
   - dataReadiness（READY / WARMING_UP / DEGRADED / FAILED）
```

# 7. Q2：中国大陆访问受限与替代托管

## 7.1 GitHub Pages 是否可行？

### 技术层面：可行

GitHub Pages 官方支持：
- 静态网站发布；
- GitHub Actions 构建/发布；
- 自定义域名；
- HTTPS。

因此 SMI 这种 Vue3 静态前端 + JSON 文件模型，从工程形态上可以迁移到 GitHub Pages。

### 中国大陆可达性层面：不建议作为主站

截至 2026 年 8 月的第三方大陆网络观测显示，`github.io` 在大陆存在大量“间歇性干扰”和部分阻断。该观测不是 GitHub 官方 SLA，但足以说明它**不能作为解决大陆可达性的确定性方案**。

GitHub 官方状态页显示 Pages 的全球服务可用率很高，但全球 uptime 不代表福建移动/联通/电信的跨境链路、DNS、TLS 和路由可达性。

### 结论

**GitHub Pages：适合作为免费全球镜像/灾备，不适合作为 SMI 的中国大陆主站替代。**

尤其本项目当前问题就是 Cloudflare anycast 在福州部分运营商不可达，换成另一个境外托管并不能消除“跨境网络路径不可控”这一根因。

# 8. `gorestart.cn` 未 ICP 备案的约束

## 8.1 核心约束

现行国内云厂商文档均明确：如果网站/域名托管或解析到中国大陆节点服务器，并对外提供网站服务，需完成 ICP 备案。

对象存储静态网站也不例外：

- 阿里云 OSS：中国内地 Bucket 绑定自定义域名，需要 ICP 备案；
- 腾讯云 COS：中国大陆静态站实践要求先备案；
- 华为云 OBS：自定义域名解析至中国大陆节点时需要备案；
- 腾讯云 EdgeOne：使用“中国大陆可用区”或包含大陆的全球区域时要求域名已 ICP 备案。

### 对本项目的直接含义

`gorestart.cn` 当前未备案：

1. 可以继续指向中国香港、新加坡、美国等非大陆节点；
2. 可以使用境外/香港对象存储或全球边缘节点；
3. **不能把它直接作为合规的大陆 OSS/COS/OBS/CDN/EdgeOne 中国大陆节点生产域名；**
4. “站点是纯静态、没有后端”不构成免备案理由。

# 9. 国内/低成本静态托管方案对比

### 成本参考（仅作当前官方公开信息摘要）

- 阿里云 OSS：新用户存在 3 个月免费试用额度；公开计费文档示例中的标准存储约 `0.12 元/GB/月`，实际还需计算请求与下行流量。
- 腾讯 COS：新个人用户当前公开文档显示有 `50GB / 6个月` 标准存储免费额度，但流量/请求等可能另计费。
- 腾讯 CloudBase：当前有免费环境和低价个人套餐；静态托管容量有免费额度，但不同套餐的自定义域能力不同，正式迁移前需按控制台当前套餐再核验。
- EdgeOne Pages：官方当前提供长期免费用量套餐，但未备案域名不能因此获得中国大陆节点加速资格。

> 不建议只看“存储免费”判断总成本；静态站真正容易产生费用的是公网下行流量、CDN、HTTPS、自定义域名及请求量。

# 10. 推荐迁移路线

## 路线 A：未备案阶段（短期）

目标：在不改变合规状态的情况下，提高大陆用户成功访问概率，而不是承诺大陆 SLA。

建议：

1. Cloudflare Pages 保留为海外主镜像；
2. 新增一个第二镜像：
   - 优先 PoC：阿里云 OSS 中国香港；
   - 备选：华为云 OBS 中国香港；
   - 可同时测试腾讯 EdgeOne Pages 的境外区域；
3. 使用独立子域名，例如 `smi-hk.gorestart.cn`；
4. 在福建移动/电信/联通 + 至少北京/上海各做持续探测；
5. 观察 7~14 天：
   - DNS 成功率；
   - TCP/TLS 成功率；
   - 首字节；
   - HTML 与 JSON 成功率；
   - 运营商差异。

**不要在没有真实三网探测的情况下宣称香港节点一定优于 Cloudflare。**

## 路线 B：备案完成后（长期推荐）

1. 完成 `gorestart.cn` ICP 备案；
2. 将中国大陆访问入口迁入大陆对象存储/静态托管：
   - 腾讯 COS 广州/CloudBase；
   - 或阿里云 OSS 华南/华东；
3. 配大陆 CDN 或 EdgeOne 中国大陆区域；
4. GitHub Actions 仍可继续作为 CI/CD，只把发布目标从 Cloudflare 扩展到国内对象存储；
5. 海外访问继续保留 Cloudflare Pages；
6. 如 DNS 服务支持线路解析，可形成：
   - 中国大陆 → 国内 CDN/对象存储；
   - 海外 → Cloudflare Pages。

这是最能从根因上解决“福州三网访问不稳定”的方案。
