## 背景事实（已发生、不可更改）
- 环境：DSH harness，主控模型 deepseek-v4-pro，子 agent 用 opencode-go/deepseek-v4-flash；编排工具 workflow() 有 600 秒 wall-clock 硬上限，超时即报错（已发生 5 次，每次约 10 分钟空转；5 次超时时文件均已写盘，说明是"任务书包含耗时自验证/网络探测"导致超限，以及单 agent 编辑两个大文件做十几项改动本身也可能超限）。
- ChatGPT 网页复核环节：发送后用 RESPONSE_PROBE 轮询，存在"回复早已完成但主控仍在前台阻塞 workflow 600 秒、未能及时取回"的实例。
- 项目 git 存在双分支维护（P0 验收器分支 + P1 采集器分支）+ cherry-pick 开销（约几分钟，次要）。
- 主控 V4 Pro 的推理本身不是瓶颈；但主控每轮工具调用之间都有推理间隔，"回合数 × 每回合开销"是真实墙钟成本。
- 子 agent 编辑速度尚可（5 次超时时文件均已写完）。

## 待复核的改进方案 v2（我上一轮自评复核后的版本）
1. 子 agent 任务书按工作量预算设计：单 agent ≤3 分钟、≤4 项精准改动；允许秒级 py_compile；禁止 pytest 全量/基线/网络探测等一切秒级以上执行；大改动拆成多个小 agent 或主控直接做。
2. 并行不受限：单 workflow 可装 2~3 个符合预算的 agent（并行 wall-clock = max 而非 sum）。
3. 主控分层：小而准的改动（≤3 个 edit、主控已掌握文件结构）主控直接 edit；大块新代码/重复性工作才派 flash agent。
4. 验证与派发并发：pwsh 后台 job 跑验证（pytest/基线），同时主控推进下一步，不阻塞。
5. ChatGPT 粗粒度交错轮询：发送后先干别的活，3~5 分钟探测一次；完成后"稳定确认（matched+generating=false+指纹两次一致）→ 取全文"两步连续执行（保留协议，不跳过稳定性确认）。
6. 单分支顺序提交（取消双分支+cherry-pick），送审引用 commit 哈希。
7. 回合内批量/并行发独立工具调用，减少回合数。
